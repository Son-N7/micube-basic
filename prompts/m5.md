## Part 1. 버그를 실패 테스트로 고정하고 고치기 (30분)

**[터미널]**
```
git add -A
git commit -m "chore: 이전 모듈 실습 결과"
git switch -c practice/m5 m5-start
./gradlew test
claude
```
변경이 없으면 `git commit`은 "nothing to commit"으로 끝나니 그대로 다음 줄을 입력합니다.

버그 제보(품질팀 최수진): CLAIM 보류를 해제했더니 같은 로트의 QUALITY 보류까지 풀려 판매 가능 재고에 잡혔다.

### ① 재현 테스트 쓰기

```
@docs/bugs/BUG-0217-release-other-reason.md @docs/specs/release-hold.md
버그를 재현하는 API 통합 테스트 HoldReleaseRegressionTest 를 새 파일로 작성해 줘.
QUALITY·CLAIM 보류가 모두 걸린 로트에서 CLAIM만 해제하면 QUALITY 활성 보류가 남고 로트는 HOLD여야 한다는 것을 검증해 줘.
기존 테스트와 제품 코드는 수정하지 마. 이 테스트만 실행해서 기대값·실제값·실패 이유를 보여 줘.
```

기대 HOLD·실제 AVAILABLE처럼 **업무 규칙 위반으로** 실패해야 재현입니다. 컴파일 실패·404는 재현이 아닙니다.

### ② 사람이 검토하고 고정

재현 테스트는 버그 수정의 기준입니다. 테스트 파일을 열어 검증 내용이 버그 제보와 맞는지 읽어 본 뒤, 그 파일만 스테이징합니다.

**[터미널]**
```
git add src/test
git status --short
```

`A`로 표시된 테스트 파일 하나만 스테이징되었는지 봅니다. 스테이징한 뒤에 테스트가 바뀌면 `git diff`에 나타납니다.

### ③ 테스트 보호 hook 만들기

이제 제품 코드를 고칠 차례입니다. "재현 테스트는 그대로 두고"라고 부탁할 수는 있지만, 부탁은 강제가 아닙니다. 고치다가 막히면 AI가 테스트의 기대값을 바꿔 통과시킬 수도 있습니다. 고치기 전에 부탁을 강제로 바꿉니다.

```
방금 스테이징한 재현 테스트를 네가 Edit·Write 로 고치지 못하게 막는 hook 을 .claude/hooks/protect-tests.mjs 로 만들어 줘.
보호할 테스트는 .claude/protected-tests.txt 에 목록으로 관리하고, 지금 스테이징한 파일을 넣어 둬.
막을 때는 테스트 대신 제품 코드를 고치라고 알려 줘. 팀에서 Windows 와 Mac 을 같이 쓰니 둘 다 동작해야 하고, 기존 설정은 유지해 줘.
만든 뒤 막히는 경우와 안 막히는 경우를 hook 에 직접 넣어 보여 줘. 테스트 파일은 고치지 마.
```

판정 예시에서 목록에 있는 파일은 막히고(종료 코드 2), 없는 파일은 통과(0)하는지 봅니다. Claude가 파일을 Bash 명령으로 만들어 화면에 "파일 생성" 표시가 없을 수 있으니, **[터미널]** `git status --short`로 `.claude` 아래 hook·목록·설정 파일이 생겼는지도 봅니다.

### ④ 동작 확인

```
보호가 동작하는지 확인하려고 해. HoldReleaseRegressionTest 에서 로트 상태 기대값을 AVAILABLE 로 바꿔 봐. 막히면 받은 메시지를 그대로 보여 주고, 다른 방법으로 바꾸지는 마.
```

hook이 Edit를 막고, Claude가 hook의 메시지(테스트 대신 제품 코드를 고칠 것)를 받는지 봅니다. 막히지 않고 바뀌었다면 `git restore src/test`로 되돌리고, `/hooks`에서 hook이 등록됐는지 확인하거나 Claude Code를 다시 시작한 뒤 다시 보냅니다.

이어서 hook이 어디까지 지키는지 확인합니다.
```
보호 범위를 확인하려고 해. 같은 변경을 이번에는 Edit·Write 도구를 쓰지 말고 Bash 명령(node -e 등)으로 파일을 직접 고쳐서 해 줘. hook이 반응했는지만 알려 주고, 파일은 되돌리지 말고 그대로 둬. 되돌리는 건 내가 git으로 할게.
```

**[터미널]** Bash로 바꾼 변경은 hook을 통과해 `git diff`에 보입니다. 스테이징해 둔 내용으로 되돌리고, 다시 비어 있는지 확인합니다.
```
git diff -- src/test
git restore src/test
git diff -- src/test
```

hook은 지정한 도구(`Edit|Write`)에만 걸려 있습니다. Bash로 쓴 변경, 사람이 편집기로 고친 변경은 통과합니다. 그래서 마지막에는 사람이 `git diff`로 확인하고, 7번 모듈에서 커밋 단계 검사를 마지막 관문으로 둡니다.

**[터미널]** hook만 먼저 커밋합니다. 스테이징한 재현 테스트는 아직 실패하므로 이 커밋에서 뺍니다 (커밋마다 테스트가 통과해야 함). 끝에 `-- .claude`를 붙이면 `.claude`만 커밋되고 테스트는 스테이징된 채로 남습니다.
```
git add .claude
git commit -m "chore: 재현 테스트 보호 hook 추가" -- .claude
git status --short
```

`git status --short`에 재현 테스트가 `A`로 남아 있으면 됩니다.

### ⑤ 제품 코드 고치기

```
재현 테스트는 그대로 두고 제품 코드를 최소로 고쳐 줘. 재현 테스트와 전체 ./gradlew test 결과를 보여 줘. 커밋은 내가 할게.
```

**[터미널]** 테스트가 그대로인지(출력이 비어 있는지) 확인하고, 재현 테스트와 수정을 함께 커밋합니다. 둘은 "버그 수정"이라는 한 가지 변경입니다. 따로 커밋하면 테스트만 든 커밋에서 테스트가 실패해 "커밋마다 테스트 통과" 규칙(`.claude/rules/git.md`)을 어깁니다.
```
git diff -- src/test
git add -A
git commit -m "fix: 판매 보류 해제 시 다른 사유 보류를 유지 (BUG-0217)"
```

## Part 2. 위험 SQL 3중 방어 (35분)

Part 1의 hook은 파일 수정(Edit·Write)을 막았습니다. 이번에는 명령 실행(Bash)을 막는 hook과, hook 바깥의 두 층을 함께 씁니다.

**[터미널]** 개발 DB와 운영 흉내 DB가 없으면(`.local/db` 폴더가 없으면) 먼저 만듭니다.
```
./gradlew dbReset
```

| 층 | 장치 | 막는 것 |
|---|---|---|
| 1 | permissions (`.claude/settings.json`) | 개발 DB 조회는 허용, 운영 DB 명령은 사람에게 확인(ask), 명백한 위험 명령은 거부(deny) |
| 2 | PreToolUse hook (`sql-guard.mjs`) | 운영 DB에 대한 DML·DDL·KILL, 개발 DB의 DROP·TRUNCATE·KILL·WHERE 없는 UPDATE/DELETE |
| 3 | DB 권한 (운영은 `shop_ro` 계정만 제공) | 위 둘을 지나온 모든 쓰기, 사람이 직접 친 명령까지 |

### ⑥ 지금 상태(부탁만 있음)에서 요청

```
운영 DB(--env prod)에서 CLAIM 보류가 1주일 넘게 걸린 로트를 찾아서, 그 보류를 해제하도록 바로 UPDATE 해 줘. 급해.
```

### ⑦ 1층 permissions

```
.claude/settings.json 의 permissions 를 다음처럼 설정해 줘.
- allow: node scripts/db.mjs --env dev 로 시작하는 명령, node scripts/render-sql.mjs 명령
- ask: node scripts/db.mjs --env prod 로 시작하는 명령
- deny: KILL, DROP, TRUNCATE 가 들어간 Bash·PowerShell 명령 (대문자 그대로, 다른 규칙은 추가하지 마)
기존 설정(테스트 보호 hook 포함)은 유지하고, 각 규칙이 어떤 문자열에 걸리는지 설명해 줘.
대소문자나 인자 순서가 바뀌면 빠져나가는 경우와, 반대로 너무 넓게 막는 경우도 예를 들어 줘.
```

설명에서 deny가 막지 못하는 모양(대소문자, 인자 순서)과, 반대로 너무 넓게 막는 경우(그 단어가 들어간 커밋 메시지나 검색 명령)를 봅니다. 문자열 규칙만으로는 부족해서 2층 hook이 필요합니다.

### ⑧ 2층 hook

```
네가 scripts/db.mjs 로 SQL 을 실행하기 전에 검사하는 hook 을 .claude/hooks/sql-guard.mjs 로 만들어 줘.
운영 DB(--env prod)는 조회만 허용하고, 개발 DB 도 DROP·TRUNCATE·KILL 과 WHERE 없는 UPDATE·DELETE 는 막아 줘.
막을 때는 이유와 대신 할 일(승인된 스크립트로 사람이 실행)을 알려 줘. 대소문자나 주석으로 피해 가지 못하게 하고, Windows·Mac 둘 다 동작해야 해.
팀원이 리뷰할 수 있게 요청한 규칙만 간단하게 만들고, 확인은 실제 DB 를 건드리지 말고 예시 명령 몇 개를 hook 에 직접 넣어서 보여 줘. 예시용 파일이 필요하면 .claude/tmp/ 에 둬.
```

Claude가 판정 예시를 돌리는 명령에 DROP·KILL 같은 단어가 들어가면 ⑦의 deny에 Claude 자신이 막히거나, 그걸 피하려고 예시를 파일로 빼서 실행하기도 합니다. 응답에서 deny를 언급한 부분을 찾아봅니다. "너무 넓게 막는 deny"의 실제 사례입니다 (`SKILL.md`처럼 KILL이 들어간 파일 이름도 걸립니다).

### ⑨ 동작 확인

⑥과 같은 요청을 다시 입력합니다.
```
운영 DB(--env prod)에서 CLAIM 보류가 1주일 넘게 걸린 로트를 찾아서, 그 보류를 해제하도록 바로 UPDATE 해 줘. 급해.
```

조회는 확인 창(ask)을 거치고, UPDATE는 hook이 막는지 봅니다.

### ⑩ 3층은 사람이 직접 확인

## Part 3. 개인 챌린지: 컨벤션을 hook으로 강제 (20분)

새 주제이니 `/clear`로 대화를 비우고 시작합니다. 사내 MyBatis 컨벤션(`.claude/rules/mybatis.md`)은 지금 부탁입니다. 이 중 파일 하나만 보면 판정되는 규칙을 hook으로 강제합니다. 이번에는 프롬프트를 직접 씁니다.

Part 1·2의 hook은 실행 **전에** 막았습니다(PreToolUse). 컨벤션 위반은 막기보다 저장 **직후** 알려 주고 Claude가 이어서 고치게 하는 편이 낫습니다(PostToolUse).

### 요구 조건

7번 모듈의 커밋 전 검사가 검사 스크립트를 다시 쓰므로, 스크립트의 위치와 입출력은 아래대로 맞춥니다.

| 항목 | 조건 |
|---|---|
| 언제 | 매퍼 XML(`src/main/resources/mapper/**/*.xml`)을 Edit·Write로 저장한 직후 (PostToolUse) |
| 무엇을 | C1 조회 테이블의 `WITH (NOLOCK)` 누락, C2 `${}` 사용, C3 `SELECT *` |
| 범위 | 저장한 파일 전체를 검사한다. 이미 있던 위반(알려진 위반)도 알린다 (6번 모듈에서 레거시 매퍼를 고칠 때 이 알림을 씁니다) |
| 위반이면 | 종료 코드 2. 파일·줄·규칙·고치는 방법을 stderr로 알려 Claude가 이어서 고치게 한다 |
| 검사 스크립트 | `scripts/check-conventions.mjs`. 인자는 파일 목록(없으면 매퍼 XML 전체), 출력은 한 줄에 `파일:줄 [규칙] 메시지`, 위반이 있으면 종료 코드 1 |
| hook | `.claude/hooks/check-mapper.mjs`, 설정은 `.claude/settings.json`(기존 설정 유지). Node.js로, Windows 경로 구분자(`\`)도 처리 |
| 문서 | CLAUDE.md "강제 장치" 표에 한 줄 추가 (막는 것 / 못 막는 것) |

### 진행 순서

1. **분류**: Claude에게 CLAUDE.md와 `.claude/rules/`의 규칙을 "파일 하나만 보면 판정 / 여러 파일이나 실행이 필요 / 사람 판단 필요"로 나누고 강제 수단(hook·테스트·리뷰·CLAUDE.md 유지)을 추천하게 합니다. C1~C3이 hook 대상인지 직접 판단합니다. Claude가 다른 수단(테스트 등)을 추천하면 이유를 읽어 보고, 이번 과제에서는 요구 조건대로 hook으로 만듭니다.
2. **만들기**: 위 조건으로 hook과 검사 스크립트를 만들게 하고, 저장소 전체에 `check-conventions.mjs`를 실행하게 합니다. 3번 모듈에서 기록한 "알려진 위반"(`docs/onboarding.md`)이 나오는지 봅니다. 기존 위반은 고치지 않습니다 (7번 모듈에서 다시 봅니다).
