## 요구사항 요약 (원문은 `docs/specs/`)

| | 보류 등록 `POST /api/lots/{lotNo}/holds` | 해제 `POST /api/lots/{lotNo}/holds/release` |
|---|---|---|
| 역할 | QC | QC |
| 본문 | `reasonCode`(QUALITY·CLAIM) 필수, `comment` 필수(공백 불가, 500자 이내) | `reasonCode` 필수, `comment` 선택 |
| 성공 | 201, 로트 HOLD, 보류 1건 기록, 수량 유지 | 200, 그 사유의 활성 보류만 해제. 다른 사유가 남으면 HOLD 유지, 없으면 AVAILABLE |

```
# ① QC 역할로 QUALITY 보류 등록 → 201
curl -s -w '\nHTTP %{http_code}\n' -X POST http://localhost:8080/api/lots/LT-261001-0001/holds \
  -H 'Content-Type: application/json' -H 'X-User-Id: qc01' -H 'X-User-Roles: QC' \

# ② 같은 요청 반복 → 409 HOLD_ALREADY_EXISTS
curl -s -w '\nHTTP %{http_code}\n' -X POST http://localhost:8080/api/lots/LT-261001-0001/holds \
  -H 'Content-Type: application/json' -H 'X-User-Id: qc01' -H 'X-User-Roles: QC' \
  -d '{"reasonCode":"QUALITY","comment":"품질 검사 대기"}'

# ③ WAREHOUSE 역할로 CLAIM 보류 등록 → 403
curl -s -w '\nHTTP %{http_code}\n' -X POST http://localhost:8080/api/lots/LT-261001-0001/holds \
  -H 'Content-Type: application/json' -H 'X-User-Id: wh01' -H 'X-User-Roles: WAREHOUSE' \
  -d '{"reasonCode":"CLAIM","comment":"고객 클레임 접수"}'

# ④ comment 공백으로 CLAIM 보류 등록 → 400
curl -s -w '\nHTTP %{http_code}\n' -X POST http://localhost:8080/api/lots/LT-261001-0001/holds \
  -H 'Content-Type: application/json' -H 'X-User-Id: qc01' -H 'X-User-Roles: QC' \
  -d '{"reasonCode":"CLAIM","comment":"   "}'
```

### ② 절차서 체크리스트로 직접 검증

`.claude/skills/add-api/`를 편집기에서 열어 아래 절차서와 대조합니다. (Claude에게 점검을 맡기지 않습니다.) 빠지거나 다른 항목에 표시합니다.

순서 (3~7번은 순서가 달라도 빠진 것만 없으면 됩니다)
- [ ] 1. 인자로 받은 명세(API, 오류 표, 확인 시나리오)를 확인한다
- [ ] 2. 기준 API(출고 API)의 코드를 확인한다
- [ ] 3. domain: 필요한 record·업무 규칙을 만든다
- [ ] 4. mapper: 매퍼 인터페이스 메서드와 XML 쿼리를 만든다 (`.claude/rules/mybatis.md`)
- [ ] 5. application: Service 메서드를 만든다 (상태 변경과 기록을 한 트랜잭션에서)
- [ ] 6. api: Request·Response record와 Controller 메서드를 만든다
- [ ] 7. 새 오류가 있으면 `ErrorCode`에 등록한다
- [ ] 8. 짝 테스트 `XxxApiTest`를 만든다
- [ ] 9. `./gradlew test`, `./gradlew checkstyleMain`을 실행한다
- [ ] 10. 결과와 명세에 없던 결정을 보고한다
- [ ] 11. 커밋 메시지를 `.claude/tmp/commit-msg.txt`에 저장하고, **커밋하지 않고** 끝낸다

매번 지켜야 할 것
- [ ] Controller 첫 줄에서 역할 확인 (`user.requireRole(Role.X)`)
- [ ] 입력 검증은 Request의 Bean Validation + `@Valid`
- [ ] 응답은 `ApiResponse.ok(XxxResponse.from(...))`
- [ ] 업무 오류는 `BusinessException(ErrorCode.X)`
- [ ] 테스트: 성공 + 해당하는 실패(입력, 권한, 대상 없음, 상태 충돌). 실패 뒤 데이터가 그대로인지까지

Skill 구성
- [ ] `SKILL.md`는 절차만 담고, 어느 단계에서 `reference.md`·`templates/`를 읽을지 적혀 있다
- [ ] `templates/`의 골격이 기준 API의 실제 코드와 같다
- [ ] `disable-model-invocation: true` (사람이 부를 때만 실행)

## 3단계: 다른 API에 Skill 적용

```
/add-api docs/specs/release-hold.md
```

도구 호출 목록에서 `add-api/reference.md`, `add-api/templates` 경로를 읽는 호출(Read, 또는 Bash의 cat)이 보이는지 찾습니다. 등록과 해제의 파일 구성·테스트 구성을 나란히 비교합니다.

끝난 뒤 확인
- `.claude/tmp/commit-msg.txt`의 내용이 해제 API 커밋 메시지로 바뀌었다 (1단계 파일이 남아 있으니 내용으로 확인합니다. 그대로면 2단계 체크리스트 11번을 다시 봅니다)
- 해제 테스트에 "QUALITY·CLAIM 중 CLAIM만 해제 → HOLD 유지" 시나리오가 있다

핵심 차이 확인: 사유별 해제, 다른 사유 유지, 남은 보류가 없을 때만 AVAILABLE, comment 선택. 등록 코드를 그대로 복사했다면 이 차이를 놓칩니다.

해제 API도 1단계처럼 서버를 띄워 직접 확인합니다. 해제는 "그 사유의 보류만 풀고, 다른 사유가 남으면 HOLD 유지"가 핵심이라, 보류 두 개를 걸어 둔 상태에서 하나씩 풉니다.

**[터미널 B]** 서버가 꺼진 상태에서 개발 DB를 처음 상태로 되돌립니다 (1단계에서 건 보류를 지움).
```
./gradlew dbReset
```

**[터미널 A]** 서버를 실행하고 켜 둡니다.
```
./gradlew bootRun --args='--spring.profiles.active=devdb'
```

**[터미널 B]** 요청 여섯 개를 **위에서부터 순서대로** 보냅니다. ①②는 해제할 보류를 만드는 준비 단계입니다.
```
# ① 준비: QUALITY 보류 등록 → 201
curl -s -w '\nHTTP %{http_code}\n' -X POST http://localhost:8080/api/lots/LT-261001-0001/holds \
  -H 'Content-Type: application/json' -H 'X-User-Id: qc01' -H 'X-User-Roles: QC' \
  -d '{"reasonCode":"QUALITY","comment":"품질 검사 대기"}'

# ② 준비: CLAIM 보류 등록 → 201
curl -s -w '\nHTTP %{http_code}\n' -X POST http://localhost:8080/api/lots/LT-261001-0001/holds \
  -H 'Content-Type: application/json' -H 'X-User-Id: qc01' -H 'X-User-Roles: QC' \
  -d '{"reasonCode":"CLAIM","comment":"고객 클레임 접수"}'

# ③ CLAIM만 해제 → 200, 응답의 status 는 HOLD (QUALITY 보류가 남아 있음)
curl -s -w '\nHTTP %{http_code}\n' -X POST http://localhost:8080/api/lots/LT-261001-0001/holds/release \
  -H 'Content-Type: application/json' -H 'X-User-Id: qc01' -H 'X-User-Roles: QC' \
  -d '{"reasonCode":"CLAIM","comment":"클레임 종결"}'

# ④ 같은 해제 반복 (comment 없이) → 409 NO_ACTIVE_HOLD
curl -s -w '\nHTTP %{http_code}\n' -X POST http://localhost:8080/api/lots/LT-261001-0001/holds/release \
  -H 'Content-Type: application/json' -H 'X-User-Id: qc01' -H 'X-User-Roles: QC' \
  -d '{"reasonCode":"CLAIM"}'

# ⑤ WAREHOUSE 역할로 QUALITY 해제 → 403
curl -s -w '\nHTTP %{http_code}\n' -X POST http://localhost:8080/api/lots/LT-261001-0001/holds/release \
  -H 'Content-Type: application/json' -H 'X-User-Id: wh01' -H 'X-User-Roles: WAREHOUSE' \
  -d '{"reasonCode":"QUALITY"}'

# ⑥ 마지막 남은 QUALITY 해제 → 200, 응답의 status 는 AVAILABLE
curl -s -w '\nHTTP %{http_code}\n' -X POST http://localhost:8080/api/lots/LT-261001-0001/holds/release \
  -H 'Content-Type: application/json' -H 'X-User-Id: qc01' -H 'X-User-Roles: QC' \
  -d '{"reasonCode":"QUALITY","comment":"검사 통과"}'
```

**[터미널 A]** `Ctrl+C`로 서버를 끕니다. **[터미널 B]** DB에서 결과를 확인합니다.
```
node scripts/db.mjs --env dev "SELECT * FROM stock_lot WITH (NOLOCK) WHERE lot_no = 'LT-261001-0001'"
node scripts/db.mjs --env dev "SELECT TOP 5 * FROM stock_hold WITH (NOLOCK) ORDER BY hold_id DESC"
```

| 확인 | 기대 결과 |
| --- | --- |
| 요청 ①–⑥ | `HTTP 201` → `HTTP 201` → `HTTP 200` → `HTTP 409` → `HTTP 403` → `HTTP 200` |
| ③의 응답 | `"status":"HOLD"`. `AVAILABLE`이면 CLAIM을 풀면서 QUALITY 보류까지 풀어 버린 것 (사유별 해제 누락) |
| ⑥의 응답 | `"status":"AVAILABLE"` |
| `stock_lot` | 상태는 `AVAILABLE`, 수량은 40 그대로 |
| `stock_hold` | 이 로트의 보류 2건(QUALITY·CLAIM) 모두 `RELEASED_AT`이 채워져 있음. CLAIM 행에는 `RELEASE_COMMENT` "클레임 종결", QUALITY 행에는 "검사 통과" |

**[터미널]** 제안된 커밋 메시지와 결과를 확인한 뒤 커밋합니다.
